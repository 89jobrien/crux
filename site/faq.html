Questions

The ones that actually come up

Answered from source, manifests, and captured runs. Where the repository disagrees with itself, the disagreement is part of the answer.

How is this different from tracing or OpenTelemetry?

A span in those systems is a timing primitive: it happened, and here is how long it took. crux:: treats a step as an epistemic primitive: it happened, and here is how sure we are the output is correct. The difference is that a step carries a confidence reading, and the whole trace is the return value rather than something exported to a collector.

The project's own summary of the distinction: tracing tells you what happened; crux:: tells you what happened and lets you re-run it from a snapshot.

The practical consequences are two. You cannot forget to attach the trace, because returning Crux<T> returns the trace with it. And replaying a function means re-running it seeded by a snapshot of that same value.

What exactly comes back from a run?

From the source of crux-schema:

pub struct Crux<T> {
  pub id: CruxId,
  pub agent: String,
  pub pipeline_version: Option<String>,
  pub value: Result<T, CruxErr>,
  pub steps: Vec<Step>,
  pub children: Vec<Crux<Value>>,
  pub started_at: DateTime<Utc>,
  pub finished_at: Option<DateTime<Utc>>,
}

Delegations nest as a tree of child values. There are accessors for the inner result, the causal chain, the delegations, the rejected branches, the duration, and the pass and fail counts, plus to_snapshot() for the replay seed.

Note that pipeline_version is in the type but is missing from the published syntax reference.

YAML pipeline or Rust macro — which should I use?

Both, and they produce the same Crux<T>. Use a .crux file when the workflow is declarative and the sequence is the point. Use #[crux::agent] when you need typed logic, delegation, and confidence-based routing that YAML would only approximate.

A .crux file has four parts: pipeline: as a name, an optional budget:, an optional display: block for human-facing titles and visibility, and an ordered steps: list. A Cruxfile is the multi-target variant, keyed on targets: instead.

How does replay decide a step still matches?

By name plus an ordinal hash. In strict mode a mismatch fails. In lenient mode the matcher does a forward name scan, so an ordinal shift is the designed recovery path rather than a fallback.

The finer detail: lenient matching rejects a candidate on differing content hashes only when both sides have one. Exhausting the candidates yields a live miss, not an error.

Every step records a StepOrigin of Live or Replayed, and the CLI prints it as [LIVE] or [CACHED / REPLAYED] beside each row.

What are the four budget dimensions?

Handler attempts, model tokens, wall-clock milliseconds, and dollars. They are measured independently, and delegated budgets are enforced in the child context rather than only at the top.

One real gotcha: BudgetDef is an untagged enum, so a compound limit such as { calls: 40, duration_ms: 900000 } matches a single variant and the other constraint is dropped without an error. This is a tracked P0. Until it is fixed, express each limit as its own entry.

Do I need an API key to run a pipeline?

Not for anything that does not call an LLM handler. --dry-run and --check resolve handlers without executing them and write no trace. The showcase fixtures run against deterministic handlers with no key at all.

The default rule planner also needs no key and makes no network call. LLM handlers need one, and CI never exercises them: the llm_extract and planner test binaries are excluded from the nextest run.

Why does checking my own example produce a dozen warnings?

Because the contract system is stricter than 1.0. A missing_contract warning means a handler's input schema or confidence capability is not fully declared. Subprocess plugins can currently only declare their output shape, so plugin steps are always incomplete under --strict.

examples/showcase.crux produces twelve of them, and that is expected rather than a broken example.

The docs and the code disagree. Which do I trust?

The code. Three specific cases where it matters:

  • CONFORMANCE.md specifies a StepKind and StepStatus that were never built. Read the enums in crux-types/src/step.rs instead.
  • CHANGELOG.md stops at 0.1.0 from April while the workspace is 0.4.0. It is not a release history.
  • docs/src/ is an orphaned tree of three-line stubs. The live book is docs/, following docs/SUMMARY.md.

The status page lists the full set of known drift.

Why is the published CLI missing most of its own subcommands?

The released binary predates develop. It exposes run, check, list, and plan. The other seven — regress, trace, replay-debug, handlers, schema, doctor, init, test — are in the source and not in the install.

There is also no --version flag at all. crux --version errors with unexpected argument.

How do I install it? The name on crates.io looks taken.

Install from git with an explicit tag rather than from crates.io:

cargo install --git https://github.com/89jobrien/crux \
  --tag v0.4.2 crux-cli

The workspace is at 0.4.0 with tags through v0.4.2. The unrelated crux crate on crates.io belongs to a different publisher.

Is for_each: parallel actually parallel?

No. The key is accepted, but iterations still execute sequentially. CruxCtx is a single mutable trace recorder, so concurrent nested ctx.step() calls are not sound without a change to crux-runtime.

An older gap-analysis document claims bounded concurrency with max_concurrency: 8. The capabilities reference supersedes it, and the older claim should be ignored.

What is the minimum supported Rust version?

1.89.0, from the rust-version field in the workspace manifest. Some agent guides still say 1.88; that is a tracked documentation TODO and the manifest is authoritative.
